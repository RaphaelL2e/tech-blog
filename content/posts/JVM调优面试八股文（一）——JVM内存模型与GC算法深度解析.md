## 一、JVM内存结构全景

JVM在运行时将内存划分为多个区域，每个区域承担不同的职责。理解这张"内存地图"，是所有调优工作的基础。

### 1.1 运行时数据区划分

根据JVM规范，运行时数据区分为以下几个部分：

```
┌─────────────────────────────────────────────────────────┐
│                    JVM 运行时数据区                      │
├──────────────┬──────────────┬───────────────────────────┤
│  线程私有     │  线程共享     │        直接内存            │
├──────────────┼──────────────┼───────────────────────────┤
│ 程序计数器    │              │                           │
│ 虚拟机栈      │     堆        │     Direct Memory         │
│ 本地方法栈    │   方法区/      │   (NIO, Netty等使用)      │
│              │  Metaspace    │                           │
└──────────────┴──────────────┴───────────────────────────┘
```

**各区域详解**：

| 区域 | 线程性 | 存储内容 | 异常类型 |
|------|--------|---------|---------|
| 程序计数器（PC Register） | 私有 | 当前线程执行的字节码行号 | 唯一不会OOM的区域 |
| 虚拟机栈（VM Stack） | 私有 | 栈帧（局部变量表、操作数栈、动态链接、方法出口） | StackOverflowError / OOM |
| 本地方法栈（Native Method Stack） | 私有 | Native方法的栈帧 | StackOverflowError / OOM |
| 堆（Heap） | 共享 | 对象实例、数组 | OutOfMemoryError: Java heap space |
| 方法区（Method Area / Metaspace） | 共享 | 类信息、常量、静态变量、JIT编译后的代码 | OutOfMemoryError: Metaspace |

### 1.2 面试高频：堆和栈的区别

这是最基本的面试题，但很多人回答不够全面：

```java
// 一行代码背后的内存分配
Person p = new Person("张三", 25);
```

- **栈**中存储：局部变量 `p`（引用指针，指向堆中的对象）
- **堆**中存储：`Person` 对象实例（包含 name="张三", age=25 的字段值）
- **方法区**中存储：`Person` 类的元信息（类名、字段定义、方法字节码）

### 1.3 面试陷阱：方法区的演进

这是面试官常用来考察知识深度的点：

| JDK版本 | 方法区实现 | 位置 | 存储内容变化 |
|---------|-----------|------|-------------|
| JDK 1.7 及之前 | 永久代（PermGen） | JVM进程内存内 | 类信息、常量池、静态变量 |
| JDK 1.8 开始 | 元空间（Metaspace） | 本地内存（Native Memory） | 类信息、常量池；静态变量移到堆中 |

**为什么用Metaspace替换PermGen？**

永久代有固定上限（`-XX:MaxPermSize`），在动态加载类的场景（如Spring、MyBatis的CGLIB代理）容易OOM。Metaspace使用本地内存，上限受限于物理内存，可以通过 `-XX:MaxMetaspaceSize` 控制。

```bash
# 查看Metaspace使用情况
jstat -gc <pid> 1000 5
# 输出中的 MC（Metaspace Capacity）和 MU（Metaspace Used）
```

## 二、对象的创建与内存分配

### 2.1 对象创建的完整流程

```java
Object obj = new Object();
```

这行代码在JVM中经历了以下步骤：

```
类加载检查 → 分配内存 → 内存空间初始化 → 设置对象头 → 执行<init>构造方法
```

**详细过程**：

1. **类加载检查**：JVM遇到 `new` 指令时，检查该类是否已被加载、解析和初始化。如果没有，先执行类加载过程。

2. **分配内存**：在堆中划分出确定大小的内存块。分配方式有两种：
   - **指针碰撞（Bump the Pointer）**：适用于内存规整的情况（Serial/ParNew收集器）。移动指针即可分配。
   - **空闲列表（Free List）**：适用于内存碎片化的情况（CMS收集器）。维护一个空闲块列表，找到合适的块进行分配。

3. **并发安全处理**：
   - **CAS + 失败重试**：对分配动作进行原子操作
   - **TLAB（Thread Local Allocation Buffer）**：每个线程在Eden区预分配一小块内存，线程内分配无锁

4. **内存空间初始化**：将分配的内存空间初始化为零值（不包括对象头）

5. **设置对象头**：设置对象的Mark Word（哈希码、GC分代年龄、锁状态等）和类型指针（指向Class元数据）

### 2.2 面试高频：TLAB是什么？为什么需要？

```bash
# JVM默认开启TLAB
-XX:+UseTLAB          # 默认true
-XX:TLABSize=256k      # 单个TLAB大小
```

**TLAB解决的问题**：堆内存是所有线程共享的，对象分配时需要同步。TLAB给每个线程在Eden区分配一块私有缓冲区，线程在自己的TLAB上分配对象，无需加锁，极大提升了分配效率。

**TLAB的局限**：当对象较大无法放入TLAB，或TLAB空间耗尽时，需要通过CAS在Eden区分配。

## 三、分代内存模型

### 3.1 为什么堆要分代？

分代的核心依据是**弱代假说**（Weak Generational Hypothesis）：

1. **绝大多数对象朝生夕死**：统计表明约90%以上的对象在一次Minor GC中被回收
2. **熬过越多次GC的对象越难以回收**：老对象往往是被长期引用的核心对象

基于这个假设，JVM将堆分为不同代，对不同代采用不同的GC策略，从而提升整体效率。

### 3.2 堆内存分代结构

```
┌──────────────────────────────────────────────────┐
│                      堆 (Heap)                    │
├────────────────────┬─────────────────────────────┤
│                    │                             │
│   年轻代 (Young)    │       老年代 (Old)          │
│   ≈ 堆的 1/3       │       ≈ 堆的 2/3            │
│                    │                             │
│  ┌────┬─────────┐  │                             │
│  │    │         │  │                             │
│  │Eden│ Survivor│  │                             │
│  │ 8  │   2     │  │                             │
│  │    │ S0 | S1 │  │                             │
│  │    │ 1  | 1  │  │                             │
│  └────┴─────────┘  │                             │
│                    │                             │
└────────────────────┴─────────────────────────────┘

比例：Eden : S0 : S1 = 8 : 1 : 1
年轻代 : 老年代 = 1 : 2
```

**关键参数**：

```bash
-XX:NewRatio=2         # 老年代/年轻代 = 2/1（默认值）
-XX:SurvivorRatio=8    # Eden/Survivor = 8/1（默认值）
-Xmn512m               # 年轻代大小
```

### 3.3 对象的晋升流程

```
新对象分配在Eden区
        │
        ▼
  Eden区满 → Minor GC
        │
    存活对象复制到S0（年龄+1）
        │
  下次Minor GC → S0存活对象复制到S1（年龄+1）
        │
  来回复制，年龄持续增长
        │
  年龄 ≥ 15（默认） → 晋升到老年代
        │
  或：S区空间不足 → 直接晋升（动态年龄计算）
        │
  或：大对象 → 直接进入老年代
```

**面试常问的细节**：

**Q: 为什么Survivor要分成两块（S0和S1）？**

A: 为了避免内存碎片。如果只有一个Survivor区，存活对象在Eden和Survivor之间复制时会产生碎片。使用两个Survivor区（S0和S1），同一时刻只使用其中一个：GC时将Eden和正在使用的Survivor中的存活对象一次性复制到另一个空的Survivor中，然后清空原来的区域。这样保证了存活对象始终在连续的内存空间中，不存在碎片问题。

**Q: 对象的年龄最大是多少？为什么是15？**

A: 对象头中的Mark Word用4个bit存储GC年龄，最大值为2^4 - 1 = 15。可以通过 `-XX:MaxTenuringThreshold` 调整（范围0~15）。

```bash
# 调整晋升年龄阈值
-XX:MaxTenuringThreshold=10   # 默认15
```

**Q: 什么是动态年龄计算？**

A: JVM并非只看对象年龄是否达到MaxTenuringThreshold才晋升。在每次Minor GC时，会计算Survivor区中同龄对象的大小总和。如果某个年龄及以下的所有对象大小总和超过Survivor区空间的一半（`-XX:TargetSurvivorRatio`默认50%），则年龄大于等于该年龄的对象直接晋升到老年代。这个机制叫**动态年龄判定**。

**Q: 大对象直接进老年代的阈值是多少？**

A: 通过 `-XX:PretenureSizeThreshold` 设置。超过这个大小的对象直接在老年代分配，避免在Eden区和Survivor区之间来回复制。

```bash
-XX:PretenureSizeThreshold=1048576   # 1MB，超过此大小的对象直接进入老年代
```

注意：这个参数只对Serial和ParNew收集器有效，Parallel Scavenge不生效。

## 四、GC Roots与可达性分析

### 4.1 判断对象存活的方法

JVM使用**可达性分析算法**判断对象是否存活，而非引用计数法（引用计数法无法解决循环引用问题）。

**可达性分析的基本思路**：

1. 选定一组根节点（GC Roots）
2. 从GC Roots开始向下搜索，搜索走过的路径称为**引用链**（Reference Chain）
3. 如果一个对象到GC Roots没有任何引用链相连（即不可达），则判定对象为可回收

```
   GC Root          GC Root
     │                 │
     ▼                 ▼
   对象A ──→ 对象B    对象C ──→ 对象D
     │                          │
     ▼                          ▼
   对象E                      对象F

   可达：A, B, C, D, E, F → 不回收
   不可达：对象G, H → 可回收
```

### 4.2 哪些对象可以作为GC Roots？

这是面试中几乎必问的考点。可以作为GC Roots的对象包括：

1. **虚拟机栈中引用的对象**：各线程方法栈中的局部变量、参数
2. **方法区中类静态属性引用的对象**：`static` 变量引用的对象
3. **方法区中常量引用的对象**：`final static` 常量引用的对象
4. **本地方法栈中JNI引用的对象**：Native方法中引用的Java对象
5. **JVM内部引用**：基本类型对应的Class对象、常驻的异常对象、系统类加载器
6. **同步锁（synchronized）持有的对象**：被 `synchronized` 锁住的对象
7. **JVM内部数据结构**：如Interner字符串、线程对象

**面试加分点**：

> 如果面试官追问"为什么静态变量是GC Root？"，可以回答：静态变量属于类级别，生命周期与类一致，类不被卸载则静态变量引用的对象不应被回收。而类的卸载条件非常严格（该类所有实例被回收、加载该类的ClassLoader被回收、该类对应的Class对象没有任何引用），所以静态变量是稳定的GC Root。

### 4.3 引用的四种类型

JDK 1.2之后，Java将引用分为四种强度（从强到弱）：

| 引用类型 | 特征 | 回收时机 | 典型用途 |
|---------|------|---------|----------|
| 强引用（Strong） | `Object obj = new Object()` | 永不回收（只要可达） | 日常编程中最常见的引用 |
| 软引用（Soft） | `new SoftReference<>(obj)` | 内存不足时回收 | 内存敏感的缓存 |
| 弱引用（Weak） | `new WeakReference<>(obj)` | 下次GC时回收 | ThreadLocal、WeakHashMap |
| 虚引用（Phantom） | `new PhantomReference<>(obj, queue)` | 随时可回收，不影响生命周期 | 跟踪对象被GC的过程 |

```java
// 软引用示例：适合做缓存
SoftReference<Bitmap> cache = new SoftReference<>(loadBitmap());
Bitmap bmp = cache.get();
if (bmp == null) {
    bmp = loadBitmap();  // 被回收了，重新加载
    cache = new SoftReference<>(bmp);
}

// 弱引用示例：ThreadLocal的内部实现
static class ThreadLocalMap {
    static class Entry extends WeakReference<ThreadLocal<?>> {
        Object value;
        Entry(ThreadLocal<?> k, Object v) {
            super(k);  // ThreadLocal用弱引用，防止ThreadLocal对象无法回收
            value = v; // 但value是强引用，可能导致内存泄漏！
        }
    }
}
```

## 五、三种基础GC算法

### 5.1 标记-清除算法（Mark-Sweep）

**工作流程**：
1. **标记阶段**：从GC Roots出发，标记所有存活对象
2. **清除阶段**：清除未被标记的对象

```
标记前：  [A] [B] [C] [D] [E] [F] [G]
              ↑   ↑           ↑
           存活  存活        存活

标记后：  [A]* [B] [C]* [D]* [E] [F]* [G]

清除后：  [A]  ___  [C]  [D]  ___  [F]  ___
                    （产生3个空闲碎片）
```

**优点**：
- 实现简单
- 不需要移动对象，STW时间短

**缺点**：
- **内存碎片**：清除后产生大量不连续的空闲块，后续分配大对象时可能失败
- **效率不稳定**：如果存活对象多，标记和清除的效率都低

**适用场景**：CMS收集器的老年代回收就基于标记-清除算法。

### 5.2 标记-复制算法（Copying）

**工作流程**：
1. 将内存分为两块，每次只使用其中一块
2. GC时，将存活对象复制到另一块空白内存上
3. 清空当前使用的内存块

```
复制前：
  使用区：[A] [B] [C] [D] [E] [F] [G]  (A, C, D, F存活)
  空白区：[ ] [ ] [ ] [ ] [ ] [ ] [ ]

复制后：
  使用区：[ ] [ ] [ ] [ ] [ ] [ ] [ ]  (清空)
  空白区：[A] [C] [D] [F] [ ] [ ] [ ]  (存活对象紧凑排列)
```

**优点**：
- **无内存碎片**：存活对象连续排列
- **分配高效**：指针碰撞即可分配

**缺点**：
- **浪费内存**：可用内存减半
- **存活对象多时效率低**：复制开销与存活对象数量成正比

**适用场景**：年轻代回收（因为年轻代大部分对象朝生夕死，存活对象少，复制开销小）。JVM的Survivor区就是复制算法的实践。

### 5.3 标记-整理算法（Mark-Compact）

**工作流程**：
1. **标记阶段**：与标记-清除相同，标记所有存活对象
2. **整理阶段**：将所有存活对象向内存空间的一端移动，然后清理边界以外的空间

```
标记前：  [A] [B] [C] [D] [E] [F] [G]  (A, C, D, F存活)

整理后：  [A] [C] [D] [F] [ ] [ ] [ ]  (存活对象向一端移动)
```

**优点**：
- **无内存碎片**：存活对象紧凑排列
- **不浪费内存**：不需要预留一半空间

**缺点**：
- **STW时间长**：移动对象需要更新所有引用，必须Stop The World
- **性能开销大**：如果存活对象多，移动开销大

**适用场景**：老年代回收（老年代存活对象多，不适合复制算法）。Parallel Old、G1的老年代回收都基于标记-整理算法。

### 5.4 三种算法对比

| 维度 | 标记-清除 | 标记-复制 | 标记-整理 |
|------|---------|---------|----------|
| 内存利用率 | 100% | 50% | 100% |
| 内存碎片 | 有 | 无 | 无 |
| 移动对象 | 否 | 是 | 是 |
| STW时间 | 较短 | 中等（存活少时） | 较长 |
| 适合代 | 老年代 | 年轻代 | 老年代 |

**面试技巧**：面试官问"为什么要分代收集"时，可以这样回答：

> 因为不同代的对象存活特征不同，可以使用不同的GC算法。年轻代对象存活率低，适合用复制算法（复制开销小，无碎片）；老年代对象存活率高，不适合复制算法（复制开销大且浪费一半空间），所以用标记-清除或标记-整理算法。

## 六、分代收集策略与跨代引用

### 6.1 分代收集策略

JVM的GC根据回收区域分为两类：

- **Minor GC / Young GC**：只回收年轻代（Eden + Survivor）
  - 触发条件：Eden区空间不足
  - 频率：高（通常几秒到几分钟一次）
  - STW时间：短（通常几ms到几十ms）

- **Major GC / Full GC**：回收整个堆（年轻代 + 老年代）+ 方法区
  - 触发条件：老年代空间不足、Metaspace空间不足、`System.gc()`调用、CMS的Concurrent Mode Failure
  - 频率：低
  - STW时间：长（通常几百ms到几秒）

### 6.2 跨代引用问题

**问题场景**：Minor GC时只扫描年轻代，但如果老年代中的对象引用了年轻代的对象，这个年轻代对象就不应该被回收。但每次Minor GC都扫描整个老年代来检查跨代引用，效率太低。

**解决方案：卡片表（Card Table）**

JVM将老年代内存划分为固定大小的卡片（Card），通常每张Card为512字节：

```
老年代内存：
┌──────┬──────┬──────┬──────┬──────┬──────┐
│ Card0 │ Card1 │ Card2 │ Card3 │ Card4 │ Card5 │  ...
│ 512B  │ 512B  │ 512B  │ 512B  │ 512B  │ 512B  │
└──────┴──────┴──────┴──────┴──────┴──────┘

Card Table（位图）：
┌───┬───┬───┬───┬───┬───┐
│ 0 │ 1 │ 0 │ 0 │ 1 │ 0 │  ...
└───┴───┴───┴───┴───┴───┘
      ↑           ↑
    dirty       dirty
```

- 每次老年代对象写入引用指向年轻代对象时，JVM在写屏障中将对应Card标记为dirty
- Minor GC时只需扫描Card Table中dirty的Card，而不需要扫描整个老年代

**写屏障（Write Barrier）**：

```cpp
// 伪代码：写屏障
void oop_write_barrier(oop* field, oop new_value) {
    oop old_value = *field;
    *field = new_value;
    // 如果新值在年轻代，且字段所在对象在老年代
    if (is_in_young(new_value) && is_in_old(field)) {
        card_table->mark_dirty(addr_of(field));
    }
}
```

### 6.3 面试高频：如何减少Full GC？

Full GC是系统性能的大敌，面试中经常被问到如何优化：

1. **合理设置堆大小**：避免堆过小导致频繁GC
   ```bash
   -Xms4g -Xmx4g   # 堆初始和最大设为相同值，避免动态扩缩
   ```

2. **合理设置年轻代大小**：年轻代太小会导致对象过早晋升到老年代
   ```bash
   -Xmn2g          # 或用 -XX:NewRatio=1 让年轻代占堆的1/2
   ```

3. **避免大对象**：大对象直接进入老年代，加速老年代填满
   ```bash
   -XX:PretenureSizeThreshold=1m   # 超过1MB的对象直接进老年代
   ```

4. **避免 `System.gc()`**：手动触发Full GC
   ```bash
   -XX:+DisableExplicitGC   # 禁用System.gc()的Full GC触发
   ```

5. **监控Metaspace**：动态类加载场景下防止Metaspace溢出
   ```bash
   -XX:MetaspaceSize=256m
   -XX:MaxMetaspaceSize=512m
   ```

## 七、总结与知识图谱

本文作为JVM调优面试八股文系列的开篇，系统讲解了JVM内存模型和GC算法两大基础模块。用一张图总结核心知识结构：

```
JVM内存模型与GC算法
│
├── 内存结构
│   ├── 程序计数器（线程私有，不OOM）
│   ├── 虚拟机栈（线程私有，StackOverflowError）
│   ├── 本地方法栈（线程私有，Native方法）
│   ├── 堆（共享，分代：Eden/S0/S1/Old）
│   └── 方法区/Metaspace（共享，JDK8后用本地内存）
│
├── 对象分配
│   ├── TLAB（线程本地分配缓冲区，无锁分配）
│   ├── 大对象直接进老年代
│   └── 动态年龄计算晋升
│
├── GC Roots（7种）
│   ├── 栈中局部变量
│   ├── 静态属性引用
│   ├── 常量引用
│   ├── JNI引用
│   ├── JVM内部引用
│   ├── synchronized锁持有
│   └── 线程对象
│
├── 引用类型（4种）
│   ├── 强引用 → 永不回收
│   ├── 软引用 → 内存不足时回收
│   ├── 弱引用 → 下次GC回收
│   └── 虚引用 → 跟踪GC过程
│
├── GC算法（3种）
│   ├── 标记-清除 → 有碎片，适合老年代
│   ├── 标记-复制 → 无碎片，浪费一半，适合年轻代
│   └── 标记-整理 → 无碎片，STW长，适合老年代
│
└── 分代收集
    ├── Minor GC（年轻代，频繁，STW短）
    ├── Full GC（全堆，低频，STW长）
    └── 卡片表（解决跨代引用扫描问题）
```

**面试高频考点速记**：

| 考点 | 关键答案 |
|------|--------|
| 堆为什么分代？ | 弱代假说：多数对象朝生夕死，老对象更难回收 |
| Eden:S0:S1比例？ | 8:1:1（-XX:SurvivorRatio=8） |
| 年轻代:老年代比例？ | 1:2（-XX:NewRatio=2） |
| MaxTenuringThreshold默认值？ | 15（4bit，范围0~15） |
| GC Roots有哪些？ | 栈引用、静态属性、常量、JNI、锁持有等 |
| 三种GC算法各适合什么代？ | 复制→年轻代，标记清除/整理→老年代 |
| Metaspace vs PermGen？ | Metaspace用本地内存，无固定上限，不易OOM |
